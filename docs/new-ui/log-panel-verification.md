## 三、DOM 裁剪压测（300 次追加）

在真实日志页面上直接注入 300 次增量追加，观察是否膨胀：

| 指标 | 压测前 | 300 次后 | 结论 |
|---|---|---|---|
| 日志块数 | 3 | **200（封顶）** | ✅ 分块裁剪生效 |
| 日志节点数 | 836 | **801** | ✅ 不升反降 |
| 日志 HTML | 69 KB | **34 KB** | ✅ 旧块被回收 |
| JS 堆 | — | 2.4 MB | ✅ 无增长 |
| 300 次追加耗时 | — | **7 ms** | ✅ 主线程无感 |

**这就是解决「运行久了会卡」的核心机制**：

1. **分块**：每次增量包进 `<div class="alas-log-chunk" style="display:contents">`
   （布局上完全透明，视觉与直插无差异）
2. **整块裁剪**：超过 200 块就 `removeChild(firstElementChild)`
   —— 不能用「逐节点删」，rich 输出的 span 之间夹着裸文本节点，
      逐节点删会残留且内存无限涨（老 UI 踩过 3.3GB 的坑，
      注释记录在 `module/webui/widgets.py:RichLog.dom_max_chunks`）
3. **增量游标**：`?since=<cursor>` 只取新增，不重传历史
4. **可见性暂停**：`document.hidden` 时不轮询

## 四、实时日志追加验证（已补，用户在挂机时实测）

> 前置：用户启动调度器（`alive:true`，跑「三油低耗」任务），日志开始持续产生。
> 方法：新 UI 打开 `22267/new/#/overview/alas`，每 5 秒采样一次 DOM 指标。

| 时刻 | 日志块数 | 节点数 | HTML | 堆内存 | 是否在底部 |
|---|---|---|---|---|---|
| 初始 | 3 | 797 | 67 KB | 2.9 MB | ✓ |
| T+5s | **4** | 802 | 67 KB | 3.4 MB | ✓ |
| T+10s | 4 | 802 | 67 KB | 3.4 MB | ✓ |
| T+15s | **5** | 817 | 68 KB | 3.5 MB | ✓ |
| T+20s | **7** | 927 | 78 KB | 2.5 MB | ✓ |
| T+25s | **1** | 789 | 66 KB | 2.5 MB | ✓ |

### 三个关键结论

1. **增量追加正常工作**：块数 3 → 4 → 5 → 7，每块对应一次 2s 轮询拿到的新日志。
2. **自动滚动一直生效**：每个采样点 `atBottom` 都是 true，日志增长时视图跟随到底部。
3. **T+25s 块数从 7 骤降到 1 是「全量重建」**：
   服务端 `ProcessManager.renderables` 是环形缓冲（上限 400），
   回绕后游标失效 → 接口返回 `full:true` → 前端清空容器只留一个新块。
   **这是设计行为，不是 bug** —— 它保证了长时间运行不会累积无限 DOM。

### 内存表现

堆内存 2.9 → 3.4 → 3.5 → **2.5 MB**（回落），
说明 GC 能正常回收被裁掉的日志块，没有泄漏迹象。

## 七、与老 UI 的关键差异（有意为之）

| 项 | 老 UI | 新 UI |
|---|---|---|
| 传输方式 | PyWebIO WebSocket push | REST 轮询 2s |
| 首屏全量 | 服务端推 400 条 | `?since=-1` 拉最近 200 条 |
| 增量 | WS 推送 | `?since=cursor` 拉取 |
| 渲染缓存 | `RichLog._html_cache` | **复用同一个**（服务端共享） |

服务端渲染链完全复用（`HTMLConsole + Highlighter + WEB_THEME + LOG_CODE_FORMAT`），
所以颜色/格式与老 UI **逐字节一致**。
